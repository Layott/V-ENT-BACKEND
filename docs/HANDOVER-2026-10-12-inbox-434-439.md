## 438 Safari: what was checked, what it probably is

- Live site in WebKit (the engine inside Safari) with Playwright: webkit-2370 installed in
  V-ENT/tasks/session-tools/webkit (`node open.mjs [origin] [paths...]`, env LOCALE=fr-FR etc.;
  in Git Bash set MSYS_NO_PATHCONV=1 or "/" becomes "C:/Program Files/Git/"). iPhone 13 and Mac,
  en-NG, fr-FR, pt-BR, 9 public pages: all 200 with their h1, no page error, no console error, no
  failed request. Remove: delete that folder and %LOCALAPPDATA%/ms-playwright/webkit-*.
- Script scan: none of the 12,646 deployed chunk files on the box uses regex lookbehind (a parse
  error in Safari before 16.4 that kills the whole file); the entry chunks use nothing old Safari
  lacks except behind a guard. Found on the way: eight client pages import `VENT` from
  `src/app/api/auth/[...nextauth]/route.js`, which drags lib/authOptions (server code, NextAuth
  providers) into client bundles. Harmless at runtime, worth untangling one day (not filed).
- TLS: chain leaf, YE1, Root YE (cross-signed by ISRG Root X2), X2 (cross-signed by X1), valid to
  2028/2032; v-ent.co and www on one cert, api and app on another; TLS 1.2 and 1.3; ALPN
  http/1.1 only; no AAAA record.
- Most likely cause: certificate transparency on the phone. The cert carries two SCTs, DigiCert
  Sphinx 2026h2 (in Apple's list since Nov 2024) and Let's Encrypt Willow 2026h2 (a tiled log, in
  Apple's list since 17 Nov 2025, list version 451). Apple needs two; a phone whose CT list
  predates that counts one and shows "This Connection Is Not Private". Apple forum thread 821806
  (April 2026) reports exactly this for iPhones upgraded from iOS 14/15 straight to 18. Not
  something the server can fix with Let's Encrypt; every LE site has the same pair of logs.
- Asked of the CEO: the exact message, the iPhone model and iOS version, Wi-Fi or data. If it is
  the CT message, the user's fix is a software update; ours would be a different CA, which is a
  decision, not a fix.
