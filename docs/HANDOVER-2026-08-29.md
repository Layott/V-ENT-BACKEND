## The two things that were broken in production

These are the ones to care about. Both had been broken since they were built,
and both were invisible to every test in the repo.

### 1. Send and Withdraw could never succeed

`/auth/wallet/send/` and `/auth/wallet/withdraw/initiate/` both refuse a request
without a `pin`. Neither page ever collected one, so every attempt came back
"recipient_username, amount, and pin are required" and the page dutifully showed
that sentence, which reads like a form complaint rather than a screen that
cannot work.

Nothing caught it because both halves were individually right and individually
tested. The backend tests sent a PIN, because whoever wrote them knew the
endpoint wanted one; the frontend was never run against a real endpoint.

- Fixed: `src/components/wallet/PinPrompt.js`, mounted on both pages, asked for
  in the last step before money moves. A refused PIN is answered on the prompt
  rather than behind it.
- Pinned by `vent_auth/tests_wallet_flows.py`, 18 tests, which is the first
  end-to-end cover the wallet has ever had.
- The class of bug is now checked: `tools/check-required-fields.py` reads the
  view's `if not all([...])` guard and the page's request body and reports a
  field the page never sends. It was negative-tested: removing `pin` from the
  send page makes it fail, restoring it makes it pass.

### 2. A deploy broke every page that was already open

`pnpm build` writes fresh fingerprinted filenames into `.next/static` and
removes the old ones. nginx serves that directory off disk. So the moment a
deploy landed, every browser holding the previous page 404'd its own stylesheet
and rendered as raw HTML inside an already-painted shell. That is the screen
recording the CEO sent.

- `deploy/deploy.sh` now carries the previous build's files forward for a week
  in `/srv/vent/frontend-static-carry`. They are content-addressed, so an old
  page asks for an old name and finds it.
- Separately: `cp -r .next/static .next/standalone/.next/static` copies INTO the
  destination once it exists. First deploy correct, every deploy after that
  buried the new files a level deeper while the originals sat there looking
  fine. Now `cp -rT`.
- nginx serves `deploy/maintenance.html` on 502/503/504 instead of its own
  error page. Self-contained, because the process that would serve its fonts
  and images is the one that is down. It retries every 15 seconds on its own.

**Neither fix is deployed.** The deploy script change only takes effect on the
run after the one that installs it.

## The attendance map, and why it is built the way it is

The risk in "show markers of people coming" is that it becomes a map of where
those people live. Three things prevent that, and all three are tested:

1. The exact point is never stored. `geo.to_cell` rounds to a 0.05 degree cell
   (about 5.5km) and there is no field on `EventAttendeeOrigin` that could hold
   the original.
2. A cell is not returned at all below `MIN_PER_CELL = 3`. Not with a count of
   one, not with a flag: absent.
3. No row exists until somebody asks for one, and only a ticket holder may ask.
   `can_share` comes from the server so the control is not drawn for anybody the
   API would refuse.

`vent_event/tests_map.py`, 23 tests, most of them about exactly these three.

## Second half of the day

### 3. The organiser console could not be reached

There were two screens for running a tournament. `/tournaments/manage?id=N` had
Match Control, Participants, Brackets, Production, **Reminders** and Player
stats. `/tournaments/<slug>/manage` had Actions, invite codes and cancel.

Every link an organiser can press - my-tournaments, the owner bar, the Manage
button - built the slug address, and **nothing anywhere linked to the console**.
So the Reminders screen built earlier the same day for "organizers should be
able to schedule reminders" existed and could not be opened, and neither could
Match Control, Brackets or Player stats.

This is the one-model-per-thing rule in the UI. Fixed the same way it would be
fixed on a model: there is one console, the slug route renders it, it takes a
slug instead of a number in a query string, and the thin page is its first tab
so nothing on it was lost. Verified on the emulator: shot 39 shows Reminders
open at `/tournaments/cade-rivalry-probe/manage`.

### 4. Link previews had no picture

An event pasted into WhatsApp came back with no banner. The tags were all
present, which is why nobody had noticed. Three things were missing behind them:

- `og:image` pointed at `api.v-ent.co/media/...`, a second host every scraper
  has to be willing to fetch from.
- There was no `og:image:width` or `og:image:height`. WhatsApp needs them.
- An organiser's banner is whatever they uploaded, and WhatsApp will not render
  much over 600KB.

`/api/og` now serves the preview image from the site's own domain, restricted to
the media host by an allow list on the URL origin - not a `startsWith` on the
string, which `https://api.v-ent.co.evil.test/` defeats. `buildMetadata` emits
the full card. `scripts/check-embeds.mjs` reads the served HTML the way a
scraper would and passes on all ten pages checked.

## The local landmine, again

`pnpm build` while `pnpm dev` is running produces exactly the unstyled screen
the CEO reported, because it rewrites `.next` under the running server. It also
damaged `node_modules` again - this time `next/dist` was gone entirely, and
`pnpm install` said "already up to date" because the lockfile matched. The
earlier probe checked `next/dist/pages`, which happened to be intact, so it
reported healthy. Deleting `.pnpm/next@...` then reinstalling breaks the peer
links; the reliable repair is `rm -rf node_modules && pnpm install`, 45 seconds.

Do not run a build while the dev server is up.
